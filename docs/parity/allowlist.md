# Intentional differences from upstream

rpyenv matches the contract of pyenv on Linux and of pyenv-win on Windows, but not their bugs (design spec §4, "Parity policy"). This file lists every intentional difference and its reason. The differential tests (M1c) read this file.

| ID | OS | Command | Upstream | rpyenv | Reason |
|---|---|---|---|---|---|
| D-01 | both | `--version`, `pyenv` with no arguments | `pyenv 2.8.8` (Linux), `pyenv 3.1.1` (Windows) | `pyenv 2.8.8 (rpyenv 0.1.0)`, `pyenv 3.1.1 (rpyenv 0.1.0)` | The output names rpyenv, and the upstream version that it matches stays parseable. |
| D-02 | Windows | `--version` | Warns when `PYENV`, `PYENV_ROOT` or `PYENV_HOME` is unset | No warnings | Advice specific to pyenv-win's installer. rpyenv doesn't need these variables. |
| D-03 | both | version files | A leading UTF-8 BOM becomes part of the first version name | rpyenv ignores the BOM | Files saved by some Windows editors would otherwise never match an installed version. |

| D-47 | Windows | `rehash` (batch tools) | A batch file in `Scripts` gets only a `.lnk` shim, which cmd can't run by name | A batch tool gets the console exe shim (the tool runs in a child cmd). A name listed in `RPYENV_BATCH_FORWARD` gets a `.cmd` forwarder that runs the tool in the caller's cmd. So the tool can change the caller's environment (unquoted arguments lose one level of `^`). `pyenv rehash` records the list in `shims\.template\batch-forward.txt` (an empty list when the variable is unset or empty). The exit check of a shim or of `pyenv exec` uses the variable when it is set, and the record otherwise. The check never rewrites the record. So a rehash that `pip install` triggers through a shim or `pyenv exec` keeps the forwarders. `pyenv.exe`'s own path never sits directly on a command line. The forwarder assigns it, once, to `RPYENV_FORWARD_PYENV` (a real Windows path can contain `&`, `(`, `)`, `^` or `%`, cmd's own metacharacters). Every later use is `%RPYENV_FORWARD_PYENV%` inside quotes. `RPYENV_FORWARD_CP` is set around the step that captures the target's path. With it set, `pyenv which` writes the path strictly in the console's active code page (what cmd's `for /f` decodes). All redirected output is in that code page (D-48). But without `RPYENV_FORWARD_CP`, a text that the code page can't represent falls back to UTF-8. `for /f` would decode that UTF-8 as the code page and garble it. So here a path that the code page can't represent fails with `pyenv`'s own message and exit 127. A name that isn't found fails the same way. `RPYENV_FORWARD_TARGET` is cleared before that step runs. So a value left over from something else can't be mistaken for this run's result. `pyenv.exe`'s own path is written absolute when it's pure ASCII. Otherwise the reference is relative to `shims`, resolved through `RPYENV_FORWARD_DIR`. `RPYENV_FORWARD_DIR` comes from a `call :d` subroutine that reads its own `%~dp0`. The reason: `%~dp0` used directly misresolves, to the current directory, for any quoted invocation, with or without the extension (`"setvar"` or `"setvar.cmd"`). Every helper variable is cleared on every exit path. Three cases have no safe reference at all, so they get the console exe shim instead of a forwarder. The first is no known `pyenv.exe`. The second is a non-ASCII `pyenv.exe` path whose relative-to-`shims` tail is also non-ASCII, or that's on another drive than `shims`. The third is a forwarded command name with a character outside `[A-Za-z0-9._+-]`, such as a space, `&` or `é`. Its name is written into the forwarder's command lines too. There are two accepted limitations. First, answering Ctrl+C's "Terminate batch job (Y/N)?" during the path-capture step can leave a helper variable set (inferred, not reproduced). Second, a cmd process started fully detached (no console at all) can fail even where an attached one wouldn't (reproduced). With no console, a non-ASCII root's `for /f` child gets its own, possibly different, console code page. | Spec §5.3, §8. |

An old version that is a symlink is replaced: only the link is deleted, and nothing is carried out of its target. Otherwise, on success, the old tree's `envs/` moves into the new tree. So does each `bin/` and `lib/python*/site-packages` (or `Lib/site-packages`) entry that the new tree lacks. For `envs/`, that is the whole folder when the new tree has none.
